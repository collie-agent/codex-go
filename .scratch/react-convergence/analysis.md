# ReAct 重复调查、耗尽轮数的诊断与优化建议

分析日期：2026-11-14。此次只分析与复现，不修改生产代码。

## 结论与证据范围

最明确的问题是：循环能识别一部分完全相同的工具调用，但缺少跨参数、跨回读的停滞检测和纠偏。工具实际执行不等于任务取得进展。调整轮数上限或继续叠加“不要重复”的提示词不能补上这个控制流缺口。

日志显示当前是 plan-execute 的 implement-refactoring 步骤。Execution summary 已记录：旧 registerExecSessionTools/sessionResponse 与新文件重复，三个注册方法有调用无定义，接下来需要修改旧文件、补齐方法并验证。但后续仍在 grep/read_file/read_tool_result/glob，反复确认同一缺口。

这是“实施未完成，反复调查”的场景，不能通过强制 completed 解决。日志片段不足以确定模型为什么选择这些调用，也不包含完整的 100 轮输出；下面的本地实验验证的是执行器允许这类停滞持续到预算耗尽，并非对真实模型的完整回放。

## 可复现结果

运行：

```sh
python3 .scratch/react-convergence/run_probe.py
```

使用 Go overlay 注入诊断测试、httptest 模拟模型，运行真实 ReactProcess 和文件工具。最终测试使用正在运行的实施步骤；将轮数上限缩为 8，避免网络、长历史和压缩干扰。工具结果均断言成功；改变 limit 的场景还断言每次实际返回内容完全一致。

| 模型行为 | 模型轮数 | 实际工具调用 | 结果 |
| --- | ---: | ---: | --- |
| 完全相同的 read_file | 4 | 1 | 连续三批重复，停止 |
| 相同文件，每轮只增大 limit | 8 | 8 | 耗尽预算 |
| 相同 grep 查询，每轮只增大 limit | 8 | 8 | 耗尽预算 |
| 读取文件后，反复回读同一 call_id 同一页 | 8 | 8 | 耗尽预算 |
| 重复 read_file 与回读同一页混在一批 | 8 | 8 | 耗尽预算 |

最后一次运行 0.428s：1 个子测试通过，4 个失败。失败断言为“无进展读取不应耗尽整个轮数预算”，诊断脚本当前预期退出码 1。普通 ReAct 版本重复运行得到相同结论，随后缩到日志对应的计划步骤场景仍然复现。文件位于 .scratch，不加入正常 go test ./...。

现有完全重复、恢复去重、失败命令重试、修复后重试等 9 个相关测试函数通过（0.648s）。格式纠错和失败重试的初始检查也通过。

## 已确认的实现缺口

1. `internal/agent/base_react.go:772`：toolInvocationKey 只规范化 JSON 键顺序、空白。limit、offset、搜索表达式变化就是不同 key；没有记录文件内容版本、已读范围和新增证据。
2. `internal/agent/base_react.go:324`：read_tool_result、exec 和进程会话操作全部绕过去重。这些工具需要允许合法重复，但目前连“相同历史结果的相同页反复回读”也没有进度约束。
3. `internal/agent/base_react.go:349`：只有整批工具都被去重，才增加 consecutiveDuplicates；任何一个 pending 调用都会清零（357 行）。混合批次可持续绕过保护。
4. `internal/agent/base_react.go:425`、`:763`：所有 exec、poll、stop 都保守地使文件观察缓存失效。避免返回旧数据是合理的，但缓存失效不能同时被解释为出现了新证据或修复。这是附加风险，未纳入本次文件读取重放。
5. `internal/agent/base_react.go:225`、`:468`：固定 100 轮；局部轮数每次 Run 从 1 开始。没有停滞后的专门纠偏阶段，也没有预算耗尽前的结构化收尾。恢复保留工具历史，但局部预算和重复计数重新初始化；应避免恢复反复刷新同一执行实例的预算。

## 建议实施顺序

### P0：增加独立的进度观察与停滞恢复

在 BaseReactProcess 的模板循环中加入小型 progressGuard，集中维护窗口统计与恢复状态；保留现有精确去重机制。无需另建代理体系或每轮增加一次 LLM 审查。

- 文件读取：按规范化路径、文件内容版本、实际返回行范围记录覆盖；换 limit 但没有新增行不算新进展。文件变化后必须允许重读。
- 搜索：结合查询范围、表达式、分页游标、返回文件/行和源码版本判断重复。不同范围的空结果可能增加排除证据，不能仅凭输出相同就拒绝所有新查询。
- 历史回读：按源 call_id 和实际字符范围记录；同一页重读、EOF 后重复读取不算新增证据。新的分页和压缩后必要的回读仍然允许。
- 混合批次：按整批结果新增的信息判断进度，不以“至少执行一个工具”清零。
- exec/进程会话：缓存正确性与进度判断分开；不能简单禁用重复测试或轮询。记录状态、cursor、输出、已用等待时间；允许合理等待，按会话截止时间收束。

可先以连续 3～5 批没有新增证据作为纠偏触发候选值，后续用真实任务调优，不能当成已经验证的最佳阈值。只读取且每次获取新证据的分析任务必须继续。

触发时先进行一次有预算的恢复决策，传入确定的重复摘要、未满足的验收条件、已有证据引用和剩余预算。例如本次日志：

> 当前步骤是实施重构。已有证据确认旧入口仍存在、三个新注册方法缺失。近期读取没有增加证据。请修改已定位的实现；如果仍缺少完成修改所必需的信息，说明具体缺口并执行一次针对性读取；若确实无法继续，报告具体原因和已修改内容。

这里的“说明”是简短行动依据，不要求模型输出内部思维过程。不能因为停滞就盲目强制写代码；也不能把无进展认定为成功。重复读写来回震荡仍须受总体预算控制。

恢复后仍停滞则进入一次有界收尾：收集已有变更、未完成项、验证结果、阻塞原因，保存检查点并失败结束；禁止编造成功。预算应为恢复和收尾预留空间，不能所有轮数耗尽后仅返回零值与错误。

### P0：让补丁错误指向可执行的修复

日志中 `target already exists: internal/mcp/exec_session.go` 在当前 `internal/mcp/apply_patch.go:123` 对应 oldPath 为 /dev/null 的新建分支。按本地实现，这是“已有文件被当作新文件创建”，不是需要重复搜索才能解决的信息缺口；未拿到原始失败补丁，不能进一步确认其整体内容。

错误反馈增加路径和建议：已有文件应使用 `--- internal/mcp/exec_session.go` / `+++ internal/mcp/exec_session.go` 修改头，不使用 `--- /dev/null`。工具说明同时给出修改已有文件的例子，避免唯一完整示例偏向创建。

### P1：把当前实施状态放在上下文显著位置

当前 `internal/context/context.go:316` 每轮传入所有步骤及较长历史报告；`internal/agent/compact.go:72` 将摘要放在正文开头，Pending 只是参考。日志中重要缺口已经记录，但没有成为明确的当前执行状态。

- 以简短区块突出当前阶段、目标文件、已完成动作、必要缺口、下一次验收、停滞计数和剩余预算。
- 完成步骤默认给出简要结论与可回读来源；保留设计提案与已验证事实的区别，不能把历史报告直接升级为源码证据。
- 将需要精确修改的目标文件片段保留在近期工作上下文中，减少“读到足够信息→被压缩→全部回读”的循环。
- 摘要合并同一事实的重复证据，避免一个 Actions 项列出大量重复读取 call_id。保留必要来源和最后有效版本。
- read_tool_result 的模型视图可以展开文本 Content，避免“JSON 字符串里再嵌 JSON 字符串”的多层转义；存储、来源及分页语义保持明确。

摘要不能无条件视为最新状态。只有在源版本未失效、所需细节已保留时才能复用；精确修改缺少上下文时仍应允许一次必要回读。

### P1：收紧规划与提示词

这次任务的“分析当前注册”和“设计拆分”高度重叠。建议此类局部重构通常使用“必要定位并实施→验证”，仅在方案存在实质不确定性时单列设计步骤。

当前系统提示词已经含有不要重复、证据充分即停止等规则。优先删减重复规则，并将“尽量选择多个调用”统一为“只选择当前阶段所必需、彼此独立的调用”。Line Protocol 决策提示只保留该返回类型需要的规则和成功/失败示例，完整解析器规范保留在文档；不改变解析器兼容能力。

上述上下文与提示词因素是待验证的贡献因素，不能从一条请求断言其导致循环。需要与相同模型、任务、初始工作区进行对照。

### P2：单独评估模型推理配置

日志的 `reasoning.effort: none` 来自 `internal/provider/responses.go:225` 的固定设置，代码说明原因为不重放 reasoning 项。不能据此断定模型能力或直接保证打开 reasoning 就能解决。

如要实验，应先核实所用服务的协议支持和工具交互续接要求，再做能力适配与单独对照；不应仅把 none 改成其他值，同时引入工具回传不兼容。本次未调用线上模型，也未验证 doubao-seed-evolving 的参数兼容性。

## 实施后的验收

- 本诊断 4 个失败场景能在预算耗尽前进入恢复或明确收尾。
- 必须补充能从“重复读取→收到恢复反馈→修改→测试→完成”的端到端测试；仅提前失败不能证明完成率提高。
- 新文件、未读区间、真实分页、修改后重读、修复后重新测试、合理进程等待均不被误拦截。
- 恢复沿用同一执行实例的预算与停滞状态；新步骤采用独立状态。工具结果未知仍遵守 ADR-0004，禁止自动重跑。
- 真实任务比较完成率、首次有效修改前轮数、无新增信息调用比例、总调用数/token、验证通过率与误判停滞率。不要只比较是否更早停止。

建议先落地进度检测、一次有界恢复、补丁纠错和结构化收尾，再分别验证上下文精简与模型配置，避免同时修改所有变量后无法判断效果。
