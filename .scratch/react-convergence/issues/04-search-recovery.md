# 04: 搜索重复调查纳入停滞恢复

**What to build:** 搜索返回没有新增信息时触发恢复，避免仅改变参数持续调查；新查询范围带来的排除证据和源码变化后的搜索仍能推进任务。

**Blocked by:** 01：文件重复读取触发有界恢复

**Status:** resolved

- [x] 搜索执行时采集查询范围、表达式、分页信息、实际返回位置及可确认的源码版本；版本信息不足时保守处理，不事后读取源码冒充查询时快照。
- [x] 同范围同表达式仅增加 limit 且未新增返回信息时累计停滞，真实分页及新增匹配位置允许继续。
- [x] 区分不同范围或表达式带来的排除证据，不仅凭输出同为空就判为重复；新查询仍受总预算约束。
- [x] 源码发生实际变化后的必要重搜允许继续，缓存失效本身不自动成为新进展。
- [x] 端到端覆盖改变 limit 返回相同内容、新范围空结果、有效分页、源码变化后重搜及混合批次，验证恢复与避免误拦截。


## Comments

2026-11-14：通过 MCP 工具响应与 ReactProcess.Run 公开边界实施 TDD。grep/glob 响应记录规范化查询、实际分页位置、EOF 与查询时可确认的版本；limit/offset 不改变查询身份。grep 查询前后分别采集符合忽略规则的文件内容指纹，一致时才确认版本；额外读取最多 16 MiB，超限或无法确认时版本未知并保守允许继续。glob 版本仅反映文件路径集合，文件内容变化不会伪造路径调查进展。

守卫按查询、版本与返回位置去重，首次空结果可作为该范围/表达式的排除证据，重复 EOF 不随 offset 增长而刷新停滞。真实新分页、新范围/表达式、源码实际变化后的必要重搜允许继续；仅缓存失效不算证据。纯缓存重复搜索与文件/搜索混合批次均同步进入恢复。运行期覆盖限制为 256 个查询版本、每个查询 4096 个位置，容量外证据保守处理；总体预算由 ticket 02 独立约束。
