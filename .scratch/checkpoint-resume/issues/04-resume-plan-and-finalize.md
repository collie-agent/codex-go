# 04: 恢复计划执行并处理最终收尾中断

**What to build:** 用户通过任一 agent 入口恢复计划执行运行时，保留原计划，跳过已完成步骤，重新执行未完成步骤；如果所有步骤已经完成，则直接使用保存的结果结束运行，不再调用模型或工具。

**Blocked by:** 02 — 按 run_id 恢复 ReAct 并保证运行互斥；03 — 计划执行全过程保存步骤检查点。

**Status:** ready-for-agent

- [ ] 两个 agent 入口按 run_id 恢复计划执行；复用运行锁、身份校验及当前配置加载规则，不创建新的 run 或 conversation。
- [ ] 按 position 加载步骤并重建执行状态，保留 step_id、revision、intent 和完成条件；当前步骤索引由有序步骤推导，不另外增加索引持久化字段。
- [ ] completed 步骤及其 Observation、CompletionEvidence 完整保留且不再执行；running、failed、interrupted 步骤恢复为 pending，再从第一个 pending 步骤开始执行。
- [ ] 已有计划和运行级验收标准不重新生成，不修改原 goal、workspace 或已确定 mode；允许通过当前 YAML 更新模型与工具设置。
- [ ] 发生在分析或规划之前的中断也可恢复：仅继续尚未完成的准备工作，已有模式、验收标准及计划不被覆盖。
- [ ] 恢复步骤状态的 checkpoint 成功后才开始执行；后续每步继续遵守运行锁及原子检查点规则。
- [ ] 当步骤全部 completed 但 run 尚未 completed 时，读取最后保存的完整执行结果，将 run 标记为 completed 并返回，不调用模型、Planner 或工具。
- [ ] completed run 再次恢复直接返回原结果；首版不提供主动暂停或服务启动自动恢复。
- [ ] 覆盖中间步骤执行前后、失败后以及最后一步提交后/运行收尾前的中断场景，断言已完成工具不再执行、未完成步骤重新执行、结果及证据不丢失。
- [ ] 验证计划恢复期间的跨进程竞争和持锁连接丢失行为；数据库故障后不再调度新工具，不引入工具副作用与数据库之间的分布式事务或人工确认。
- [ ] 覆盖两个入口的新任务到恢复的端到端路径，确认普通 ReAct 不写步骤、纯 MCP 服务无需数据库及原有 agent 流程没有回归，并更新完整恢复示例。
