# 02: 按 run_id 恢复 ReAct 并保证运行互斥

**What to build:** 用户通过任一 agent 入口显式恢复普通 ReAct 运行，保留原身份和目标，从原目标重新执行未完成任务；已完成任务直接返回保存的结果。同一运行跨进程只能有一个执行者，崩溃后可以重新取得执行权。

**Blocked by:** 01 — 新建 ReAct 运行并持久化完整生命周期。

**Status:** ready-for-human

- [x] CLI 和 agent-server 均提供按 run_id 显式恢复的入口；恢复不要求新的任务目标，也不创建新的 run 或 conversation。启动时不自动恢复遗留任务。
- [x] pending、崩溃遗留的 running 和 failed run 均可恢复；运行和会话 ID、goal、已有验收标准保持不变。
- [x] 普通 ReAct 从原 goal 重新开始，不恢复逐轮模型消息或工具调用结果，不产生步骤记录。工具自行保证重复操作幂等，不增加人工确认流程。
- [x] completed run 直接返回保存的完整结果和答案，不启动模型或工具，不重新执行任务。
- [x] 恢复使用调用时提供的当前 YAML、模型与工具配置；拒绝修改原 goal、workspace 或已确定 mode。不从步骤是否存在推断执行模式。
- [x] 新运行与恢复运行均使用按 run_id 命名的 MySQL GET_LOCK，在执行前通过专用连接取得锁；锁被占用时立即明确报错，不等待另一运行结束。
- [x] 所有 checkpoint 使用持锁连接写入；持锁连接失效时取消执行，停止后续工具调度，不通过连接池中的其他连接继续写入该运行。
- [x] 正常完成或失败后释放锁；进程崩溃导致连接断开后，由数据库释放锁，之后可显式恢复。不同 run 的锁互不阻塞。
- [x] 不引入租约、续租、过期时间或租约版本字段；不在运行过程中长期持有覆盖工具执行全过程的数据库事务。
- [x] 使用实际 MySQL 连接验证锁竞争、锁释放、持锁连接断开及重新接管；验证不同 run 可独立执行。
- [x] 验证两个入口的失败重试、崩溃恢复、completed 结果重放、配置更新及目标/工作目录/模式修改拒绝行为，并更新恢复命令的帮助及使用说明。
