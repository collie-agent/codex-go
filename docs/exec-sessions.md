# 服务启动与逐步验证

`exec` 同步等待命令结束，适合构建、测试和一次性验证。服务启动后还需要由 agent 决定后续验证步骤时，使用进程会话工具：

| 工具 | 参数 | 结果 |
| --- | --- | --- |
| `exec_start` | `command`、可选的 `args` | 立即返回 `session_id`，启动过程及错误通过轮询读取 |
| `exec_poll` | `session_id`、可选的 `cursor` 和 `wait_ms` | 增量 stdout/stderr、`next_cursor`、`state`，结束后包含 `exit_code` |
| `exec_stop` | `session_id`、可选的 `cursor` | 停止并等待沙箱清理，返回退出状态和剩余日志 |

与 `exec` 一样，入口白名单、只读运行时目录、网络及环境授权由宿主配置。不同工具调用中的沙箱拥有不同网络命名空间；要让验证命令访问已启动服务，需要宿主显式设置 `exec_network: host`。

将以下配置合入现有 Agent YAML，保留项目所需的其他工具：

```yaml
exec_network: host
base:
  allow_tools:
    - exec
    - exec_start
    - exec_poll
    - exec_stop
```

例如，agent 先调用：

```json
{"command":"go","args":["run","./cmd/server"]}
```

取得 `exec_start` 返回的 `session_id` 后，通过 `exec_poll` 检查就绪日志：

```json
{"session_id":"返回的 ID","cursor":0,"wait_ms":1000}
```

`running` 表示启动尚在进行或进程仍活跃，并不表示服务已经就绪。轮询直到日志确认监听成功，再通过 `exec` 运行项目的接口验证脚本，根据响应继续验证；不要仅等待固定时长就判定成功。后续轮询使用前一次的 `next_cursor`。

验证完成或失败时，调用 `exec_stop`，将最后的 `next_cursor` 作为 `cursor`，检查 `state: exited`。停止先向沙箱内进程组发送 SIGTERM，给服务两秒退出时间，再强制关闭沙箱；独立进程组中的后台子进程也会被清理。Linux 上使用 pidfd 等待沙箱 init 退出，确认包括监听端口在内的进程资源已释放；无法确认清理完成时返回 `error_kind: cleanup`。`go run` 的启动器与编译后的子进程都会被清理，但启动器可能先退出，不能据此保证应用的优雅退出回调完成。

日志游标是 stdout 和 stderr 共用的绝对字节偏移，省略时为 0。每个进程会话保留最近 64 KiB 日志；请求游标落在已丢弃的区域时返回 `truncated: true`，并提供当前保留的日志。`wait_ms` 默认为 0，范围为 0–1000；它限制单次轮询等待时间，不影响进程存活。相同参数可以重复轮询，仍保留的已退出会话可以重复停止。每次 `exec_start` 都创建新进程，即使命令相同；重启前应停止旧会话。

自然非零退出通过 `exit_code` 返回；参数、沙箱启动、超时和清理失败会返回工具错误。超时保留已有日志，返回 `error_kind: timeout`。显式停止不会把正常取消包装成工具错误，但应检查真实退出码。会话最长存活时间受宿主工具超时约束，上限五分钟，结束时还可能需要等待清理宽限期。每个 MCP 连接最多保留 32 个会话；全部活跃时拒绝新启动，容量满时新启动可以回收已退出会话。

进程会话归创建它的 MCP 连接所有，其他连接不能轮询或停止。当前每个 ReAct 执行使用独立连接，所以会话不会跨执行步骤、子代理或恢复保留。执行正常结束、失败或主动中断时清理其全部进程；外部 MCP 收到 EOF 或终止通知时也等待清理。进程崩溃时由沙箱的父进程死亡机制兜底。恢复后的旧 ID 会明确返回未知会话，agent 可以根据任务需要重新启动服务。stdin 为 EOF，不支持交互输入或 PTY。

ReAct 会拦截同一执行中工具名与参数相同的重复命令。成功调用 `exec_start` 或 `exec_stop` 后，之前的 `exec` 去重记录会失效，以便根据新的进程状态重新验证；文件工具的去重记录不受影响。如果连续三轮调用全部因重复而被拦截，运行会返回明确错误并结束，避免持续消耗模型请求。`exec_stop` 仅停止指定进程会话，不代表任务完成；任务结束仍需模型返回最终结果。
